# 版本迁移指南

本指南用于组织社区参与的大版本迁移，避免把不同加载器、映射和资源格式的改动混入同一个提交。

## 当前分支

| 分支 | 含义 |
| --- | --- |
| `main` | Minecraft Forge 1.20.1 的当前维护版本 |
| `port/1.21.1` | 从当前 `main` 创建的 1.21.1 迁移工作分支 |

旧的 `1.21.1` 分支只是历史快照，不应继续作为新的迁移基线。

## 迁移原则

1. 先通过“版本迁移任务”Issue 表单认领模块。
2. 目标加载器必须由维护者明确确定；不得在同一迁移中混用 Forge 与 NeoForge API。
3. 以 `port/1.21.1` 为目标分支，每个 Pull Request 只迁移一个可验证模块。
4. 先保证行为一致，再考虑利用新版本 API 重构。
5. 不修改模型资产许可，不从 JAR 解包素材，不公开分发迁移测试 JAR。

## 推荐拆分

- 构建脚本、Mappings、Forge/NeoForge 与 GeckoLib 依赖。
- 注册链：物品、方块、实体、声音、粒子和附魔。
- 鸟类基类、AI、导航、种群与迁徙。
- 单个物种及其模型/动画控制器。
- 相机、照片网络协议和服务端存储。
- 风翎扇、投射物和专属附魔。
- 数据包、配方、战利品表、标签与语言。
- 客户端渲染、GUI、Mixin 和兼容性。

## 完成标准

一个迁移模块只有同时满足以下条件才算完成：

- 目标环境可以编译和启动。
- 单人世界与独立服务端均无客户端类加载崩溃。
- 原版本的核心行为有对应实机验证。
- 新增/修改 JSON 可解析，注册 ID 与资源路径一致。
- 没有用占位实现跳过功能，也没有顺手重写无关模块。
- Pull Request 清楚列出尚未迁移或无法验证的部分。

迁移完成前，`port/1.21.1` 不应被描述为可用版本，也不应创建正式 Release。
